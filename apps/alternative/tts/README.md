# Shared Text-to-Speech service

This directory supplies the isolated main-process TTS service used by the Reader and Alternative applications. It uses Node built-ins; the bundled CPU adapters and their platform assets are separate from the conversation database and original application settings.

## Persistence and defaults

- `tts-settings-v1.json`: validated provider profiles and presentation/cache options. TTS, thinking-bubble speech, persistent audio caching, optional settings, speed and volume controls on the TTS bar are off initially. Streaming and `preferApiCache` (Prefer API recordings) are on, and master playback volume starts at 100%.
- `tts-credentials-v1.json`: optional AES-256-GCM encrypted credentials, with per-entry random salt/nonce and a scrypt-derived key. Passphrases are never stored. Saved credentials start locked after restarting; session-only credentials never enter this file. Credentials are bound to the provider and canonical endpoint.
- `tts-cache/index-v1.json` and content-addressed audio files: optional cache. Keys include source/message identity, normalized speech text, voice/model/engine revision, synthesis instructions and response format. Playback rate is excluded. Each new recording also stores an opaque digest of its normalized spoken text and source/message identity for reuse across generation-setting changes; spoken text is not stored in cache metadata. Pinned clips survive age expiry and automatic eviction, and saving audio never replaces their bytes, including when the original file is missing or corrupt. When protected clips fill the limit, speech still plays without saving another clip.
- Completed conversation recordings are also retained in RAM for the current application session, even with persistent caching off. This LRU keeps at most three recordings within the saved `sessionCacheMaxMiB` limit: 32, 64, 128, or 256 (default 64). The Playback control labels these binary memory sizes as MB. Lowering the saved limit immediately evicts the oldest recordings to fit, without cancelling synthesis or changing a buffer already delivered for playback; increasing it preserves existing entries. The per-recording 64 MiB audio limit is unchanged. Closing and reopening the TTS bar can reuse retained recordings without another provider request. Previews and interrupted or failed recordings never enter this cache; unsaved preview settings cannot resize it. Application shutdown clears it; no session-retention audio is written to disk.
- `tts-session/`: temporary CPU output and runtime caches, removed after generation or cancellation. Cache-off mode does not read or persist audio in `tts-cache`.

For the same source, message, and normalized spoken text, playback and availability share this priority: a valid pinned recording; an API recording when `preferApiCache` is on; an exact synthesis-key recording; otherwise new synthesis. API includes self-hosted speech, ElevenLabs, OpenRouter and OpenAI, regardless of the currently selected provider. Thus an API recording may be reused instead of CPU generation or a newly selected API voice. Turn off the preference and unpin any matching pinned recording to intentionally generate with changed settings. Within each priority, the most recently used recording wins, then the newest creation time, then the key. Persistent candidates require `cacheEnabled`; retained session candidates remain eligible with disk caching off. A RAM copy inherits a disk pin only when its digest and size match the original pinned recording. Invalid or expired unpinned files do not qualify; valid pins ignore age expiry. Older entries without a content digest remain eligible only through their exact synthesis key.

The service never modifies the existing application settings or conversation database. Invalid TTS configuration falls back to disabled defaults without overwriting the invalid file until the user explicitly saves settings.

## Providers and long messages

Pocket TTS and Kokoro use the verified bundled CPU assets. The current OpenAI adapter is **OpenAI**, using `/v1/realtime` and 24 kHz PCM, with no microphone input or tools. It checks the completed returned transcript against each requested section before exposing audio. This comparison is a provider-transcript check, not independent recognition of the generated audio. The retiring official OpenAI `/v1/audio/speech` adapter is not present.

Self-hosted endpoints support localhost, LAN and remote HTTP/HTTPS servers; ElevenLabs and OpenRouter use their fixed HTTPS endpoints. Self-hosted servers are not launched by the application. All remote requests are explicit, bounded, cancellable and have no automatic retry or provider fallback. Redirects are rejected so credentials cannot be forwarded to another address.

Streaming starts playback as audio becomes available. Pocket emits its native PCM output from one warmed process; Kokoro keeps one loaded ONNX session and emits audio from short sentence sections. PCM API responses are forwarded incrementally using the declared sample rate and channels. MP3 and other formats use short completed sections as a fallback; OpenAI Realtime sections are released only after transcript verification. Turning streaming off buffers the complete reading before playback. Compatible PCM WAV sections are joined into one WAV for the completed cache/replay copy; other formats retain ordered `audioClips`. No word timestamps are fabricated. Input is limited to 100,000 characters / 256 KiB, and the complete reading is bounded to 64 MiB. Limit failures are explicit; text is never silently truncated.

## IPC contract

`createTtsService({profileDir, assetsDir, onEvent?})` returns `invoke(action, args)` and `dispose()`. The caller must supply absolute application-controlled paths and enforce the existing trusted-main-frame IPC boundary.

- `tts.settings.get`, `tts.settings.save {settings}`
- `tts.synthesize {requestId,text,sourceId,messageId,thinking?}`
- `tts.preview {requestId,text,settings,apiKey?}` for an unsaved draft test. It works with master TTS disabled, cannot read or write the audio cache, and does not save settings or credentials.
- `tts.availability {messages:[{id,text,sourceId,messageId,thinking?}]}` returns `{revision,items:[{id,available}]}` in request order. A batch has at most 64 unique correlation IDs (up to 200 characters each) and shares the 512 KiB IPC request limit. It uses the same pinned/API/exact reuse policy as synthesis, saved settings, and normalized spoken text. Only complete session recordings or enabled, valid, unexpired disk recordings qualify; master/thinking restrictions still apply. It returns no audio, cache keys, paths, or credentials and does not synthesize, populate the session cache, change LRU order, or update persistent usage timestamps.
- `tts.cancel {requestId?}`
- `tts.playback {requestId,cacheKey?,active}` to restore or release disk/session protection during replay. A null or omitted key resolves the matching completed request identity.
- `tts.providers.discover {provider,endpoint?,apiKey?}`
- `tts.credentials.status`
- `tts.credentials.set {provider,endpoint?,apiKey,remember?,passphrase?}`
- `tts.credentials.unlock {provider,endpoint?,passphrase}`
- `tts.credentials.forget {provider,endpoint?}`
- `tts.cache.list`, `tts.cache.pin {key,pinned}`
- `tts.cache.preview {filter}`, `tts.cache.delete {token}`

Streaming publishes request-scoped events `{requestId,purpose,state:'audio',clipIndex,audioBase64,mime,complete:false}` before generation completes. Purpose is `conversation` or `preview`, so previews stay in the settings player. Each chunk is a standalone playable file, including WAV-wrapped native PCM; a playable chunk does not make the whole recording complete. Status events identify native PCM, progressive sections, transcript-verified sections, buffered output or cache playback accurately. Successful final results and `ready` events explicitly carry `complete:true` and `recording:{provider,model,voice}` identifying the audio actually delivered. Cache replay audio events also carry this recording identity before playback, and replay audio/ready/final results include `cacheReason` (`pinned`, `api`, or `exact`). Clients must use this identity rather than the currently selected provider/voice when labeling reused audio. Final streaming results include `streamed:true` and `clipCount` in addition to the completed replay audio; the UI must not append that completed audio a second time. A cancelled or failed request never returns a completed result. Playing an interrupted recording again requires an explicit new generation request; there is no silent retry or paid-provider fallback.

The separate `{state:'availability-changed',revision}` event asks the UI to refresh visible message indicators after completion/eviction, relevant saved settings changes, deletion, pinning, or a configured disk-expiry deadline. Settings events occur after applying the new state and before the save resolves. Availability responses identify their snapshot revision; clients discard responses older than the newest event or their current message/settings context. Initial checks establish the state after application startup. Disk verification hashes through 64 KiB stream chunks and memoizes the result against file identity, size, modification/change timestamps and recorded digest; it never retains the audio. A later lookup revalidates missing, replaced, or modified files.

Single-file synthesis returns `{requestId,audioBase64,mime,complete:true,cacheKey,cached,cacheSource,recording,sessionRetained,stored}`. Multipart synthesis replaces the single-file audio fields with `audioClips:[{audioBase64,mime}]`. `cacheSource` is `session`, `disk`, or null for newly generated audio. Every completed conversation has a `cacheKey` as its replay identity, including RAM-only recordings; this key does not imply a persistent file exists. `stored` reports persistent storage, and previews always have a null key and `sessionRetained:false`. Audio stays protected until `tts.playback` releases it, `tts.cancel`, or another synthesis request. A blank session-only credential clears the unlocked/session key while retaining any encrypted saved key.

Deletion filters use `scope` (`all`, `conversation`, `provider`, `older`, `selected`, `incomplete`) and the appropriate `sourceId`, `provider`, `olderThanDays` or `keys`. They apply to matching session recordings as well as files; all-cache deletion also clears eligible session copies. Pinned clips require explicit `includePinned:true`; active playback is always protected. Session-only recordings are not listed as persistent files: `tts.cache.list` adds a separate `session:{count,totalBytes,maxEntries,maxBytes}` summary. Deletion previews/results retain disk `count`, `bytes`, and `protectedCount`, with separate `sessionCount`, `sessionBytes`, and `sessionProtectedCount`. Preview tokens expire after two minutes and are single-use; deletion rechecks protection and clip identities. Tokens hold lightweight session identities, never audio buffers. Explicit `complete:false` disk entries cannot be reused; schema-1 legacy entries without that field remain compatible and must pass file-size and digest verification before reuse.

## Verification

Run `node --test tts/test.cjs` from an application source root. The regression tests use temporary profiles, local HTTP/WebSocket servers and generated test PCM; they do not contact paid providers. Barriers verify playable audio before completion, preview isolation, cancellation of late chunks, stable replay data during eviction, and stale availability snapshots across settings changes. Cache-policy coverage checks cross-setting pinned/API reuse, the preference toggle, read-only availability, deterministic priority/ties, original replay metadata, disk-disabled access, normalized text/source/message isolation, legacy exact compatibility, and immutable pin bytes through corruption, regeneration and restoration. Availability coverage also checks exact recording identity, batch limits, read-only/LRU behavior, valid persistent reuse after restart, memoized hashing, size/digest corruption, missing files, incomplete recordings, expiry/pins, cap changes and deletion. Other coverage includes the four RAM settings, old-file defaults, immediate shrink/enlarge behavior, session reopen without regeneration, shutdown clearing, strict completion metadata, legacy disk compatibility, active/pinned deletion protection, credentials, long messages, network bounds and Realtime transcript validation.

Actual paid-provider access requires the user's credentials and account/model access. Tests of the Realtime protocol do not claim a paid live request was made.
